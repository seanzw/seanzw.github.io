Create New Clang Builtin: Atomic FAdd

2020/05/29

Builtin Function in Clang

Similar to gcc, clang provides many useful builtin functions, e.g. __atomic_fetch_add() series to specify atomic operation and memory order requirement, but programmers (you) always want something more :) Recently, I have this problem of write code for floating point atomic operations, e.g. addition. I found these information:

  • std::atomic<> provides a fetch_add() for integer and pointer types, but floating point versions are defined in C++20, and my clang 10 has not supported it yet. Therefore, I can not specify an atomic floating point addtion in native C++ (yet).
  • Compilers (gcc and clang) provide a bunch of __atomic_xx builtin functions, which are used to implement std::atomic<>. Of course, these builtins have no floating point versions.
  • On the other hand, LLVM has atomicrmw instruction, which allows the operation to be floating point addition (fadd). On my x86 machine, an atomicrmw fadd is compiled into a small compare-exchange loop in assembly code.

One may wonder what is the point to express in atomicrmw fadd when the hardware has no support for it. You can write your own compare-exchange loop in C++ or with inline assembly. Well, a single atomicrmw instruction makes it much simpler to compiler analysis in LLVM IR than a loop. However, clang does not support inline “LLVM IR”. To compile into a single atomicrmw instruction, I had to add a new clang builtin __atomic_fetch_fadd(), which is self-explainatory.

Before diving into the details, notice that I use clang 10 and have not tested for other versions.

Declare our New Builtin

Thanks to tablegen, it is straightforward to declare a new builtin function. Add this to clang/include/clang/Basic/Builtins.def:

ATOMIC_BUILTIN(__atomic_fetch_fadd, "v.", "t")

Here v. specifies the function signature to void(...), and t means using special type-check rules. Details can be found in the comment.

Pass the Semantic Check

Clang checks that atomic builtins have correct integer types, which is not true for our __atomic_fetch_fadd. You can find this in clang/lib/Sema/SemaChecking.cpp:

if (IsAddSub && !ValType->isIntegerType() && !ValType->isPointerType()) {
    Diag(ExprRange.getBegin(), diag::err_atomic_op_needs_atomic_int_or_ptr)
        << IsC11 << Ptr->getType() << Ptr->getSourceRange();
    return ExprError();
}

It is actually easy to extend this for __atomic_fetch_fadd. I will not bother you with the details here.

Code Generation

Next we come to code generation. But before that, clang assumes integer type for atomic builtins, and casts all operands and return values to integer type. We have to fix that first, and then specify the operation to fadd. Again you can check the patch for source code.

Try It!

Finally, let’s try some code! Here is a sample c code:

#include <stdio.h>

float v = 0.0f, u = 0.0f;

int main() {
#pragma omp parallel for
  for (int i = 0; i < 10000; i++) {
    __atomic_fetch_fadd(&v, 1.0f, __ATOMIC_RELAXED);
    u += 1.0f;
  }
  printf("Final value v = %f, u = %f.\n", v, u);
  return 0;
}

Compile and check the LLVM IR:

> clang test.c -fopenmp -O3 -emit-llvm -S -o test.ll
> cat test.ll | grep "atomicrmw"
  %22 = atomicrmw fadd float* @v, float 1.000000e+00 monotonic

Finally, compile into binary and run.

> clang test.ll -fopenmp -O3 -o test
> ./test
Final value v = 10000.000000, u = 2500.000000.

The result is correct. You can check the assembly code to see how atomicrmw fadd is compiled on your machine.
